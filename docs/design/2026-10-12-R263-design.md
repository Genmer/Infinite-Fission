## 0. 概述

一句话：**祝福词条升级为「可附赠武器的局外付费自选」**——武器绑定词条不再被首发适配门静默滤除，而是上池并标记「附赠武器」，选中即开局送对应武器+挂词条生效（难度门/大关门对送通道开例）；同时祝福从免费记忆携带改为**每次出发携带消耗新局外货币「星尘」**（白10/蓝20/紫30/金50），星尘由每局结算按表现产出，形成「打局赚星尘 → 花星尘买祝福（可能带武器）→ 更强构筑打更深局」的局外小循环。收费同时是送武器的天然平衡缓解（送武器词条多为紫/金档，30/50 即门槛）。

## 0.1 数据勘误（对任务简报）

简报称「CRITICAL_MASS=required_class=melee 无指定武器」。实读 `resources/traits/MEC_CRITICAL_MASS.tres:15` 为 `required_weapon = [&"W8_orbit_field"]`、rarity=3（金）。**全仓 required_class 词条仅 1 条**：MEC_BULLET_PARRY（`required_forms:[3] + required_class:["melee"]`，rarity=1 蓝）。本设计按 .tres 实数据展开（数据驱动，无 id 硬编码原则不变）。

## 1. 核心循环

```
打一局（构筑→波次→死亡/通关）
   └→ 结算：星尘 +N（波次+击杀+难度+通关加成）
        └→ 大厅祝福面板：看余额 → 按价签选祝福（白10/蓝20/紫30/金50）
             ├→ 通用词条：开局挂上生效（现状体验，仅加付费）
             └→ 武器绑定词条：开局「附赠」对应武器+挂词条（新体验）
                  └→ 更强的开局构筑 → 打得更深/更爽 → 更多星尘 → 买更高档祝福
```

- **为什么有趣**：玩家每分钟的局内循环不变（R252 祝福本就服务于「开局定轴」）；本批把「开局定轴」从手枪兼容子集扩到全构筑空间（武器族词条首次可开局成立），并把「带不带祝福」从无脑 yes 变成一局一次的经济决策。
- **10 分钟后留住玩家的是什么**：档位阶梯（普通通关≈蓝、困难≈紫、地狱≈金，见 §5 节奏表）形成「打得起本难度档祝福」的进度感；攒 50 星尘带金档「临界质量+天狼刀」开局是明确的短目标。
- **防无脑**（用户原话目的）：免费时代每个有解锁词条的玩家理应局局带最强；收费后金档=约 1 次地狱通关的全部产出，选择即成本。

## 2. 机制细节 · 需求一：祝福送武器

### 2.1 词条→武器映射（送哪把）

新增静态解析口 `MechanicGate.blessing_gift_weapon(p_td: TraitData, p_weapons) -> StringName`（**定落 MechanicGate static**——两门矩阵所在类，BlessingPickUI 附赠行可静态复用同源结果；p_weapons=registry.weapons 由调用方注入，MechanicGate 保持无 registry 实例依赖——weapon_allowed 纯静态纪律同源；纯数据判定零 rng）：

1. **入送通道条件**：词条 params 含 `required_weapon`（单值/数组均可，R65 双口径）**或** 含 `required_class`。二者皆无（纯 required_forms 形态类如 AFF_RANGE[3]/MEC_FRACTAL[0,2,3]、无键通用词条）→ 返回空串，**不进送通道**（维持不适配不上池——形态类无法唯一确定送哪把，硬选一把属过度设计）。
2. **候选集**：
   - 有 required_weapon → 候选 = 其武器列表（巨刃 5 把全候选）；
   - 仅 required_class（BULLET_PARRY）→ 候选 = registry 全武器中 `form==MELEE(3)` 且 `melee.weapon_class ∈ required_class` 者（实际 = W8_orbit_field、W13_great_sword；**talisman 法器三把天然排除**——weapon_class 英文串对齐 card_generator.mount_gate_allows 同源口径）。
3. **选择规则（全确定性、与存档状态无关——「同一词条恒送同一把」，付费选择必须可预期）**，排序键依次：
   - ① `WEAPON_DIFFICULTY_GATE` 最低优先（入门武器优先：环绕族/巨刃恒送 W8 天狼刀=近战批首位/挡弹 30% 基线款，而非阔剑）；
   - ② `WEAPON_UNLOCK_MAPS` 最早优先；
   - ③ id 字典序兜底。
   - **排序坑（必守）**：候选拍序载体必须 `Array[String]` 字典序——Godot 4.3 的 `Array.sort()` 对 StringName↔StringName 比较无 variant case，**排序静默无效**（`_blessing_pool` :1940-1942 既有坑注释同源）。
   - **否决「图鉴已解锁优先」**：送出武器随存档状态漂移（这次裂空剑下次天狼刀）破坏可预期性，且可能恒送比入门款更强的武器；记入 §8 开放问题供下游复议。
4. **送得出 = 候选集非空**（全部 24 条武器绑定词条按数据恒送得出；未来新词条数据驱动自动覆盖）。

预期映射表（测试可直接锁，分析批 13 行验证通过）：巨刃/谐振轨道/链式引爆/临界质量/环绕三件套/弹反刀意 → **W8_orbit_field（天狼刀）**；刀势如风 → W9_arc_slash（旋风刀）；W4 族 7 条 → W4_pulse_beam；W5 族 4 条 → W5_prism；引信涂层/蜂巢挂架 → W6；定向爆破 → W7；回旋远掷 → W10。

### 2.2 池放行规则（第五滤三态化）

`_blessing_pool` :1958 第五滤从布尔改为三态：

| 判定 | 结果 |
|---|---|
| 适配首发（_blessing_fits_start_weapon 通过） | 上池，**普通项**（现状行为不变） |
| 不适配，但 `MechanicGate.blessing_gift_weapon` 送得出 | **上池，标记附赠武器**（新） |
| 不适配且送不出（纯形态类/前置组合/阈值型） | 不上池（现状不变） |

池构成变化（分析批池算术证实：**73 − 7×TH_ − 2×requires_trait = 64 = 38 适配 + 24 送武 + 2 形态出局**）：手枪首发全池由 38 项（探针 A 臂）→ **62 项**，分档 **{白 6, 蓝 24, 紫 26, 金 6}**（2 形态出局 = AFF_RANGE/AFF_CDR 两条纯 required_forms 失配蓝档词条，无 required_weapon 不进送通道，维持出局）。

### 2.3 装备链与挂载（`_apply_start_blessing` 扩展）

挂载口 :2101 在既有流程中插入送武分支（顺序敏感，逐条）：

1. 每日守卫（:2107 不变）、记忆读取/悬空守卫（不变）。
2. **先按现状找适配宿主**：槽序 0→6 首个 `mount_gate_allows` 通过者（R252 语义不变——**fits 优先于送**：fission 自定义首发恰=绑定武器（如首发 W8 选环绕词条）→ 直接挂 slot0，**不送只挂**，照常扣费）。
3. 全槽不适配 → 调 `MechanicGate.blessing_gift_weapon(td, registry.weapons)`：
   - 送不出 → 维持 R262 拒挂横幅（现状兜底，理论只剩纯形态类记忆词条走到这）。
   - 送得出 → **统一扣费时序**（§3.3 合流定案）：① 余额检查前置（不足→横幅披露返回，**不送不挂不扣**）→ ② `player.add_weapon(registry.get_weapon(wid))`（:969 首个可用槽——slot0 被首发占 → 恒落 **slot 1**）+ `attach_trait(td)` **双成功**（`Meta.mark_weapon_codex(wid)` 随装随记：白拿口径先例 :827，幂等不增 _run_weapons_drawn，军火大亨成就不受扰）→ ③ **扣费+写即落盘** → ④ 横幅。
4. **适配既有武器路径同一时序同一账**（① 余额检查前置 → ② attach 成功 → ③ 扣费+落盘 → ④ 横幅）——收费挂祝福、附赠送武器，两条路径同一序；**全链无任何「先扣后退」路径**（add_weapon 返 null/送不出等失败一律在扣费前早退）。
5. **槽位时序结论**：开局解锁槽恒 ≥2（player.gd:159 难度默认 2/3/3）→ slot1 恒空（非 echo）→ 送武器**无槽位解锁时序冲突**；SLOT2_UNLOCK_WAVE=2 解锁的槽 2 及 Boss 槽解锁链**完全不受影响**（不预支、不占用）。
6. **echo（随机双武装）边界**：困难/地狱开局 3 槽（双武装占 0/1、送武落 2，正常）；**echo×普通**仅 2 槽全被占 → add_weapon 无可用槽 → 按「无空槽」拒送拒挂 + 横幅披露「本局武器槽已满，祝福未生效」。该组合罕见（echo 为困难通关解锁角色，普通局用 echo 属自我削弱），披露即可，不做预支槽位（缓办 §8）。

### 2.4 门例外范围（定案）

- **难度门（WEAPON_DIFFICULTY_GATE）：送通道开例**（用户拍板）——普通局祝福可送 W8/W9/W11/W12/W13。
- **大关门（WEAPON_UNLOCK_MAPS）：送通道同样开例**。理由：①按效果判读用户意图——验收标准是「开局祝福面板能选到武器内容」，保留大关门会在第 1-3 关普通局继续复现同一投诉（巨刃/环绕族全绑 3/4 关武器）；②门的 设计意图是约束**局内随机获取**的节奏（mechanic_gate.gd:139-141「门只收窄来源侧上架」），祝福送武器是**局外付费自选通道**，玩家明码消费、明知道会拿到什么，渐进揭示不适用；③平衡由星尘价签承担（§4）。
- **两门开例仅限送通道**：局内卡池/商店/echo 双武装的 `weapon_allowed` 判定**一行不动**（G10 对照断言）；fission 首发难度门 :1547 不动。
- **送出武器计图鉴**（mark_weapon_codex）：是——与首发手枪/echo 双武装同口径；图鉴解锁面反而成为「以后局内也能抽到」的正反馈。

## 3. 机制细节 · 需求二：祝福收费（星尘）

### 3.1 货币定义

- **名**：**星尘**（代码/存档前缀 `stardust`）。取意：祝福=许愿，星尘=愿望的燃料；与既有局外货币「裂变结晶」（养成/角色专用）**双轨并存互不兑换**，与局内金币（商店）三轨隔离。
- **图标**：TextureFactory 新程序化 maker `stardust_icon()`（四芒星、暖金色调，具体色值实施时对齐 PopPalette 既有暖色）。
- **显示位置（三处）**：①祝福面板 footer 余额行（消费现场，§2.6）；②结算屏产出行（ earning 现场，§3.7）；③大厅养成面板头部结晶行下追加一行「星尘：%d（每局结算产出·祝福携带消耗）」（menu_screen.gd:2152 邻区，货币可见性锚点）。

### 3.2 购买语义（定案）

- **每次出发携带消耗**（一次性消费，非买断解锁）——用户目的「限制无脑使用」的唯二合理实现之一，且与「每把打完给一些」的流式经济自洽。
- 记忆键交互（逐场景定案）：

| 场景 | 行为 | 费用 |
|---|---|---|
| 面板选中「出发」 | 写记忆键（现状）→ 进局挂载成功时扣费 | 扣 |
| 记忆祝福默认带上（未开面板直选，如记忆合法且面板被跳过？——**不会发生**：池非空恒弹面板；此行覆盖未来程序化路径） | 挂载成功即扣 | 扣 |
| 「不选祝福」 | 本局无祝福、记忆不覆盖（现状） | 免费 |
| 「清除记忆」 | 清键（现状） | 免费 |
| 余额不足（记忆项不可负担） | 不挂载不扣费+横幅（§2.7）；面板不预选+置灰 | 0 |
| 每日局 | 全链路无祝福 | 0 |
| restart_run 重挂 | 同局重试 | **不扣** |
| continue_run | 恢复已购局状态 | 不扣 |

- 跨难度/跨首发携带沿用 R262 全档口径（收费不改开放面，只加价）。

### 3.3 扣费时序与已购位（防套利核心）

- **扣费时序（唯一实现序，与 §2.3-3 合流）**：**余额检查前置（不足即拒、不送不挂不扣）→ add_weapon+attach 双成功 → 扣费+写即落盘 → 横幅**。全序同步执行于同一调用栈（无 await 间隙）——「先挂载后扣费」不存在可观察中间态；**无任何「先扣后退」退款路径**（无槽/死卡/送不出等失败一律在扣费前早退，add_weapon 返 null 即中止）。
- **写即落盘**（同 set_blessing_trait 先例）：防「挂载后强杀进程→重进白得」。检查→挂载→扣费同帧同步，杀进程落在窗口内的唯一后果是「本局未记账」（下次出发按新局重新扣费），无套利面。start_run 非热路径，单次落盘成本可接受。
- **已购位**：GameLoop 新局级布尔 `_run_blessing_paid`——start_run 头部复位 false；start_run 路径首次成功「挂载+扣费」置 true；restart_run 重挂**仅当已购位为 true**（false = 本局从未买成——死亡结算补了星尘也不许重开白捡，堵「首局买不起→死亡结算+星尘→重开免费挂载」套利）。
- `_apply_start_blessing(p_allow_charge: bool)`：start_run 传 true / restart_run 传 false（内部再查已购位）。

### 3.4 Meta 新接口（meta_manager.gd）

- `var stardust: int = 20`（初始 20 = 启动资金，见 §5.4）；`var stardust_total: int = 0`（累计获取，遥测/未来成就）。
- `const BLESSING_COST := [10, 20, 30, 50]`（rarity 索引 0-3——用户拍板价，唯一真源）。
- `func blessing_cost(p_rarity: int) -> int`；`func charge_stardust(p_amount: int) -> bool`（不足/非正数返 false 不动账；成功扣+落盘）；`func grant_stardust(p_amount: int)`（结算入账，随结算统一 _save，不单独落盘）。
- 存档键：`meta/stardust`、`meta/stardust_total`（_save :1281 邻区 / _load :1319 邻区，**与 crystals 同 meta/ 段**——blessing_trait 在 characters/ 段互不相扰）；旧档缺键 → 20/0（零迁移代码的一次性全民启动资金）。

### 3.5 产出公式（定案，初始值待调参）

结算入账（`_settle_run_result` :1055 crystals 行邻区，每日分流提前返之后）：

```
星尘 = ceil((W + K/50) × D) + (胜利 ? V : 0)
  W = 本局最高波次（_run_max_wave）   K = 本局击杀（_run_kills）
  D = 难度系数 [1.0, 1.5, 2.0]        V = 通关加成 [8, 12, 16]（普通/困难/地狱）
```

- **胜利位**：Meta 局内标志 `_run_victory`——GameLoop 通关点写入（`_victory_settle_pending=true` 处 :1372 邻区，调 `Meta.mark_run_victory()`），`_reset_run_counters` :1099 复位。**不用「W≥final_wave」近似**（死在 final_wave 当波会误判通关——波次达到≠波次清空）。
- **无尽合并**：通关后选无尽继续 → 结算合并至死亡一次执行（R62 现状），W/K 取全程最深值，V 加成一次——深打多得，无双重计费面。
- **三终局口径**：死亡 = 给（GAME_OVER 结算）；通关 = 给（延迟结算在 settle_now 兑现，R62 链不变）；**中途退出（暂停回菜单）= 0**——与结晶口径完全一致（结算只挂 GAME_OVER 态），且堵「刷波次低成本退出」。
- **每日局 = 0**（每日分流提前返 :1044 天然覆盖——不给不扣，口径对齐结晶）。
- **防刷边界**：死亡→重开→死亡每循环都全额结算（与结晶同暴露面，per-GAME_OVER 结算先例）；K/50 占比压至次要（50 杀=1 尘），主收入来自波次推进，挂机刷怪收益边际。单日无硬上限（结算天然以真实局时长为限）。

### 3.6 结算屏披露（game_over_screen.gd）

- show_summary（死亡）/ show_victory（通关）统计行（:83）下**新增一行**「◆ 星尘 +N（余额 M）」。
- **通关延迟结算时序**：胜利屏出现时 settle 尚未执行（R62 待决）→ 屏上数值走**纯预览口** `Meta.stardust_for(wave, kills, difficulty, victory)`（公式单源，settle 与预览共用；不改状态）；实际入账仍走 settle 原路径。死亡屏时序无此问题（结算先于屏显）。
- 每日局结算屏：不显示星尘行。
- 现状缺口顺带披露：结晶产出结算屏本就不可见（本批不做，§7 可选）。

## 4. 合流论证：收费 = 送武器的平衡缓解（显式绑定）

- 送武器词条 24 条中**紫 15 / 金 2 / 蓝 7 / 白 0**——普通局带近战/法器最便宜的入口是蓝档「弹反刀意/谐振轨道/刀势如风」（20 星尘 ≈ 1 次普通通关），强族核心（环绕三件套/巨刃=30，临界质量=50）各有价签门槛。
- 双门开例（§2.4）放开的获取面**只经祝福付费通道**：局内随机获取仍全门禁——数值膨胀被「花钱+单件+紫/金档为主」三重限流。
- 反向绑定：没有收费的送武器 = 普通局免费白得地狱级构筑起点（金档临界质量送 W8），必然超模；收费让「送」成为可定价的商品。**两个需求互为成立的条件**，须同批交付。
