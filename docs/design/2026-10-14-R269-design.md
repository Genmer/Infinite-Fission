## 1. 概述与项目背景

一句话：把「降画质保帧」从散落的自动降级（用户感知不到、也关不掉）升级为**用户可见、可关、mobile 默认开的显式模式**，同时补上物理残差的逐桶归因键与敌侧绘制降载，让 vc80 日志能直接读出下一刀该砍哪。

现状事实（本会话亲证）：
- 项目 Godot 4.3，mobile 覆写 gl_compatibility，`display/window/stretch/mode="viewport"` + `aspect="expand"`（project.godot:36-40〔实证〕，R203 定案：720×1280 设计分辨率内部渲染、GPU 上采样——这是本批分辨率降档杠杆的物理基础）。
- 已有自动调速器 PerfGovernor（R220）：perf_mode 0=帧率优先（默认）/1=特效优先 × tier 3/2/1 自动升降；消费点=fx_quality_cap（enemy.gd:388-389〔实证〕唯一产品消费）、结算帽、派发帽、永存弹配额、R268 P4 预热门、R229 池阀。**它管的是「模拟/结算成本」，从不管 GPU 填充率与绘制量**——渲ms 15-17.2 顶死正是它够不着的轴。〔v2〕注意「唯一产品消费」的精确含义：ElementalFxLayer._fx_quality()（:83-90〔实证〕）**不在此列**——它直读 Meta.settings 不经调速器帽（见 §3.3 必改1）。
- 跳字帽现状：`popup_manager.gd:59-73` max_active_for = 桌面 80/40/20、mobile 高档满载 24；R220 修轮曾**撤销**「调速器档位接跳字帽」（越权、无用户裁定），撤销注释原文在 :69-72〔实证〕——本批重立为**模式键显式接管**（用户已授权），与撤销理由不冲突：不再是调速器暗耦合，而是用户开关。
- 密度帽现状：敌同屏 120（enemy_spawner.gd:13 const MAX_ONSCREEN〔实证〕，超帽排队不丢弃）；**敌弹无 team-1 专项帽**（唯一界=全场软 1500（balance_tables.tres:21）+ 敌数×开火），任务书「敌弹 450」为深载观测量级（vc78 弹N 总量峰值带 250-357，含玩家弹）——本批新立 team-1 模式帽 320。〔v2〕team-1 活口现状无任何直读键（弹N 不分队伍）——B 轨补观测面（§3.6 必改4）。

- vc78 关键行（深载）：fps 20-34、渲ms 15.0-17.2、物步µs 59k-143k、dc 438-958、尖峰跳 46-161ms；敌 0 间歇行渲ms 8.6-12.6/fps76-120（差距纯由负载量决定——策略降载有效的直接证据）。

## 2. 核心循环（本批的「为什么有趣」）

这是性能/策略批，不是玩法批，双循环如下：

- **玩家体验循环**：深载掉帧 → 用户打开「保帧模式」（一次设置）→ 帧率回到 40-55 → 战斗反馈密度仍够（暴击/反应大字必显；〔v2〕音效门独立后战斗听感保留——必改3）→ 玩家留在战斗而不是卸载。模式的可关性（mobile 默认开但可关、桌面默认关）保证「策略不越权」：不接受的玩家逐位回到现状。
- **诊断循环**：真机导出 1Hz 日志 → 行尾新桶键（死µs/警µs/桶µs/延µs/释N/敌弹N/拒N）直接指认物理残差真凶与 team-1 量级 → 下一批正刀有靶 → 每批 vc 轮日志复核。B 轨不是优化，是把「59k-143kµs 残差」这句 30 次改不动的模糊答案变成可指名的桶。

## 3. 机制细节

### 3.1 A 轨：保帧模式（perf_boost）——模式边界与档位

**命名**（避免与既有 perf_mode 0=「帧率优先」标签撞车）：设置键 `perf_boost`（0/1），UI 行名「保帧模式」，循环值 **关 → 开·画质85% → 开·画质75% → 关**；第二键 `boost_res`（85/75，仅 perf_boost=1 时有意义）。诊断行状态键 `促%d`（0=关/1=开85/2=开75）。

**〔v2·必改3/意见7〕设置行写口关系（写死，防显示态与 促%d 不一致）**：行内 cycle 一次写两键——85 档=`set_setting("perf_boost",1)`+`set_setting("boost_res",85)`；75 档=同上 75；关=`set_setting("perf_boost",0)`（boost_res 保留当前值不回写，重开沿用）。`促%d` 读口=perf_boost==0 ? 0 : (boost_res==75 ? 2 : 1)（单源纯函数 `PerfGovernor.boost_diag_state()`，诊断行与设置行同源）。

**注册**（照 R194/R220 双注册先例，meta_manager.gd:303-383〔实证〕）：
- `SETTINGS_DEFAULTS` 增 `"perf_boost": 0`、`"boost_res": 85`；`_normalized_setting` 增两分支（`bool(p_value)` / `clampi(int(p_value),75,85)` 后再归到 {85,75} 集合，脏值归 85）。
- **平台分叉默认（〔v2·必改5〕垫值点修订）**：SETTINGS_DEFAULTS 是 const 无法平台分叉——垫值点放 **`_ready()` 内 `_load()` 调用之后**（meta_manager.gd:571-573〔实证〕，紧邻 `_apply_fps_cap()` 同款「_load 后应用」先例位）：读档后若 `perf_boost` 键缺省，mobile 垫 1、其余垫 0（**不落盘**，首次用户显式改动才随 set_setting 落盘；旧档降级不崩口径与 R194 同款）。v1 原方案的「_load 末尾」在首启无档路径不可达（_load:1410-1411 early-return〔实证〕）——mobile 首启恰是「默认开」的主场景，v2 迁点后两出口皆达。垫值逻辑做成纯函数 `static func _boost_default_for(p_mobile: bool) -> int`（headless 可测，含首启路径断言 §5-a1）。
- **读口**：`PerfGovernor.boost_mode() -> bool`（静态，读序 `boost_override`（新测试注入口，-1=真值/0=强关/1=强开，mode_override 同款先例）> `Meta.settings("perf_boost")`）；`PerfGovernor.boost_res_notch() -> int`（85/75）。每读直查零订阅（frame_priority 同款契约）。

**与 PerfGovernor tier1-3 自动调速器的关系（定案，防两套打架）**：
- **模式=手动钉地板，不参与自动降档**：boost 不改 tier 真值、不进 EMA/转换判定、不触发 R221 Fix B 有效性校验——调速器继续按自己的节拍管理结算帽/派发帽/预热门/池阀。
- **两系统共享面恰两处，均为「boost 只会更省」的单向阀**：①`fx_quality_cap()`——boost 分支插在 tier_override 注入之后（注入优先序保测试通道），返回 0 压过一切 tier 映射（tier1 本就 0、tier2/3 被 boost 压 0）；②`_deathpop_cap_on()`——boost 分支插在 -2/-1 哨兵之后、mobile 门之前（§3.3）。两处都无「boost 抬升」反向路径，不构成回路。（〔v2〕音效档口 §3.3-A6 是第三处挂点但方向相反——「boost 开=不受渲染降级牵连」，属保护性旁路而非降载阀，同样无回路。）
- boost_res 两档（85/75）**纯手动**，不做「tier 钉 1 后自动再降」——自动升降分辨率会与 EMA/refresh_cap/fps_cap 三层已有阈值系统叠加出不可判读的行为，本批明确不做（列 §9 开放问题供下批复议）。

### 3.2 A-1 渲染分辨率降档：实现路径（本模式最大 GPU 杠杆）

**路径定案：`Window.content_scale_size` 降档 + `Camera2D.zoom` 补偿**。调研结论（引擎语义，R203/R195 两条既有真机经验背书）：
- 本项目 viewport 拉伸模式下，根视口内部渲染分辨率=content_scale_size（720×1280 经 expand 适配窗口纵横比，R203 实证 720 内渲+GPU 上采样真机有效）；**4.3 无 2D 渲染缩放专用 API**（`content_scale_factor` 仅 canvas_items 模式语义、`scaling_3d_scale` 仅 3D）——唯一受支持的内部降分辨率杠杆就是 content_scale_size，R195 已在真机运行期热切 `content_scale_aspect`（game_loop.gd `apply_stretch_aspect_clamp()` :3490-3502〔实证〕〔v2 勘误：v1 误写引擎内部名 `_update_viewport_size`〕），同一视口尺寸更新通路，运行期切 size 可行性有项目内先例。
- **〔v2〕分析轮实测收录**：content_scale_size 运行期热切已在真实 GPU 窗口（桌面 Vulkan Forward+）实测通过——720×1280→612×1088→复原两帧内生效、`get_texture().get_image()` 分辨率精确随动（直接证明内部分辨率重分配）、采样非黑（分析报告 §「实测记录」）。**残余风险收敛为 Android GLES3 真机一项**（§3.2 冒烟门不可因此降级）。
- 直接缩 content_scale_size 会**缩小坐标空间**（expand 下可见世界从 720×~1559 缩到 612×~1325）=玩法可视区变化，不可接受。**补偿**：游戏有全局 Camera2D（game_loop.gd:3399-3403〔实证〕，锚 `res_logic×0.5` 居中、make_current；分析轮核实全库唯一 Camera2D、零既有 zoom 写点——boost 应用器=首个写点）——`camera.zoom = Vector2(612/720, …) = 0.85`（Godot 4 zoom<1 为拉远）后，可见世界 rect 数学上逐位还原为 720×~1559。出生点/场地/反弹沿全在**世界域**（enemy_spawner.gd:236-246 用 res_logic〔实证〕、playfield_outline.gd:31 用 res_logic〔实证〕），相机补偿后零变化。
- 安全区自动正确：SafeAreaHelper 经 `root.get_final_transform().affine_inverse()` 换算（safe_area_helper.gd:40〔实证〕），base 缩小后 stretch 比例自动进换算，insets 恒贴屏幕物理边缘。
