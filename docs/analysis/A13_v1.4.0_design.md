## §1 C1 MetaStore 扩展

### 1.1 常量（封闭表，MetaPanel 行序一致）

| 常量 | 值 | 语义 |
|---|---|---|
| `SOFT_CAP` / `SOFT_CAP_RATE` | 500 / 0.5 | 死亡结转金币→结晶软上限（超出部分 floor ×0.5） |
| `REACTIONS` | 13 键 | 反应图鉴封闭表（剧变 6 → 增幅 3 → 共鸣 4；行序 = 反应册行序） |
| `RESONANCE_SEEN_KEYS` | FIR/ICE/LTG/WAT → res_* | 共鸣 Element 枚举 → REACTIONS 键映射 |
| `ACHIEVEMENTS` | 10 条 | 成就封闭表 `{title, desc}`（行序 = 成就页行序） |

REACTIONS 行序冻结：`rxn_fir_ice / rxn_fir_ltg / rxn_ice_ltg / rxn_wat_ice / rxn_wat_ltg /
rxn_wat_fir`（碎裂/过载/超导/冻结/导电/汽爆）→ `amp_melt / amp_quench / amp_vapor`
（融化/淬火/蒸发）→ `res_fire / res_ice / res_ltg / res_wat`（火/冰/雷/水之共鸣）。

### 1.2 API

- `static convert_gold(p_gold) -> int`：≤500 全额（负钳 0）；>500 超出部分 ×0.5 向下取整
  （600→550 / 1000→750）。
- `mark_chip_seen / mark_relic_seen(p_id: StringName) -> bool`：空 id / 已见 → false；
  首见 → String 键置位 + save + true。
- `mark_reaction_seen(p_id: String) -> bool`：非封闭表 → push_warning + false；首见 →
  置位 + save + true。
- `chip_seen / relic_seen / reaction_seen` 查询；`has_achievement / unlock_achievement`：
  未知 id → warning + false；已解锁 no-op false；首解 → save + true。
- `static reaction_seen_key(p_rxn: int) -> String`：ReactionType 六值映射（未知 → ""）。

### 1.3 存档布局（五节，save_version=1 双向兼容）

```
[meta]          save_version / crystal
[levels]        String(id) 五键
[stats]         total_runs / total_kills / best_wave
[seen]          chips / relics / reactions 三键（各 Dictionary：String id → true）
[achievements]  逐成就 id → true
```

v1.3.0 旧档缺 `[seen]`/`[achievements]` 节 → 读侧静默空（零迁移）；v1.4.0 新档被旧版读 →
旧版忽略未知节。脏值防御：`[seen]` 值非 Dictionary → warning + 空；Dictionary 内逐键
`typeof(k)==TYPE_STRING` 收录（悬空键容忍——封闭性只在 mark 时仲裁）否则跳过。

## §2 C2 追踪接线

| 站点 | 位置 | 收录/判定 |
|---|---|---|
| 芯片 | `ChipHandler.equip` 成功尾（DebugStats 后 return 前） | `mark_chip_seen` + `on_chip_equipped(max_main_count(), equipped.size())` |
| 遗物 | `RelicHandler.activate` 成功尾 | `mark_relic_seen`（null 守卫） |
| 剧变 | `ElementalSystem._trigger_reaction` 入口位（首行注释后） | 六键全收录——★先于一切早退（Boss 免疫冻结早退亦标） |
| 增幅 | `consume_amplify` 三分支各 DebugStats 后 | amp_melt / amp_quench / amp_vapor |
| 共鸣+武器 | `rebuild_registries` 函数尾（早退不含） | counts[e]≥2 → `mark_reaction_seen(res_*)`；`on_weapon_slots_changed(filled)` |

- `ChipHandler.max_main_count() -> int`：equipped 按 stat_key 计数取最大（ach_chip_set 阈值）。
- `filled`：rebuild 循环内 valid WeaponBase 分支计数（ach_weapons5 阈值）。
- GameLoop boot 注入序：AchievementTracker 构造+setup 在 `meta_store.load_save()` 后、
  xp 掉落订阅前（★铁律 6：enemy_killed/wave_started 订阅先于 EnemySpawner 入树与掉落侧）；
  elemental 注入在 chip_handler 注入旁；relic/chip 处理器注入在各自 setup 之后。

## §3 C3 AchievementTracker 与死亡结算

### 3.1 判定站点（五处）

| 成就 | 站点 | 阈值 |
|---|---|---|
| ach_boss1/2/3 | `_on_enemy_killed`（四层守卫：is Enemy → data null → TAG_BOSS 位 → data.id 三档精确匹配） | E6_boss1/2/3 各自独立，不回溯 |
| ach_wave10/20/30 | `_on_wave_started` | ≥10 / ≥20 / ≥30 |
| ach_chip_set / ach_chip_full | `on_chip_equipped` | max_main_count ≥2 / equipped ≥6 |
| ach_weapons5 | `on_weapon_slots_changed` | filled ≥5 |
| ach_kills1000 | `on_run_settled` | meta_store.total_kills ≥1000（record_run 之后） |

### 3.2 解锁仲裁 `_try_unlock`

meta_store null → return（降级）；`has_achievement` → 幂等短路；`unlock_achievement` 失败 →
return；成功 → `_new_unlocks.append` + 本地信号 `achievement_unlocked(id, title)` +
`DebugStats.count(&"achievement_unlocked")`。`reset_run()` 仅清 `_new_unlocks`
（已解锁持久在 MetaStore）。

### 3.3 死亡结算改造（`GameLoop._settle_run`）

序冻结：`_settled_this_run` 一次闸 → `gain = MetaStore.convert_gold(maxi(gold, 0))`
（★软上限折算，局内金币余额不折）→ add_crystal → record_run →
`achievement_tracker.on_run_settled(meta_store.total_kills)`（★先于取清单）→ save →
`set_crystal_gain(gain)` → `set_new_achievements(new_unlock_titles())` → 菜单统计行回写。
meta_store 缺失降级路径不变（set_crystal_gain(0)）。

### 3.4 GameOverScreen 新成就行

`_new_achievements_label` y660 f15 TOP_WIDE 居中（结晶行 624 与既有控件无交集）；
`set_new_achievements(p_titles: Array)`：空 → 隐藏；非空 → `"新成就：" + " · ".join`；
`new_achievements_text()` 观测口。成就解锁即时跳字：GameLoop 订阅本地信号 →
`show_text_popup(player 上方 -64, "成就达成：%s")`（popup/player null 守卫）。

## §8 假设清单（H1~H4，未决风险显式化）

- **H1 图鉴数值段统一受 balance 闸**：剧变/增幅数值段读 `GameConfig.balance`
  （reaction_table / amp_*_factor），共鸣段值取 ElementalSystem 模块常量但渲染同样以
  balance 就绪为前置——三组统一「balance 未就绪不附数值、无字面量兜底」。依据：boot 早期
  balance 恒已就绪，该闸纯防御；风险：与「共鸣常量恒可用」读法分歧 → 仅影响极端时序渲染，
  无逻辑面。
- **H2 软上限只折结算**：`MetaStore.convert_gold`（结算金币→结晶）与 `ChipHandler.convert_gold`
  （Boss 芯片转金币定价 ×0.5）为同名不同义；局内金币余额、商店定价、金币关奖励均不折软上限，
  仅 `_settle_run` 入账折算。依据：软上限语义只在「局外货币产出」面；风险：玩家体感 500+ 金
  局收益减半 → 数值面由 PROGRESS 留痕观察。
- **H3 击杀档读累计、Boss 不回溯**：ach_kills1000 判定读 `record_run` 之后的 total_kills
  （本局击杀计入）；Boss 三档精确匹配 id，杀 boss3 不解锁 boss1/boss2（表驱动无累积语义）。
  依据：A13 冻结方案「三档精确匹配」；风险：无。
- **H4 图鉴网格固定 12/11**：芯片格 12 / 遗物格 11 为出厂 registry 规模锚定；registry 超编
  只显示 String 升序前 N，悬空 seen 键容忍收录但渲染时 registry 缺资源按「未收录」降级。
  依据：数据封闭（12 chips / 11 relics）；风险：未来扩编需改 MetaPanel 网格常量（非本版范围）。
