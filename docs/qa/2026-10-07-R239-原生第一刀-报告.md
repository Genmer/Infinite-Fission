## 2. 桥接设计（要点）

**数据面（GDScript → C++ 单向喂入，一次喂入多次查询）：**

1. SpaceGrid 在 `rebuild()/insert()` 期同步维护**原生镜像**两数组（仅 `_native_on` 实例）：
   - `_nat_cells: PackedInt32Array`——插入序 cell 索引（`_cell_index` 现成产物，零重算）；
   - `_nat_pos: PackedVector2Array`——插入序位置（与 `_snap_pos` 逐位同值）。
2. **惰性冲刷**：`_nat_dirty` 置位（rebuild/补插），首次原生查询时一次 `feed_snapshot(_snap_items, _nat_cells, _nat_pos)`——C++ 侧建 CSR（计数→前缀和→按插入序散布），此后多次查询零重建。无 snap 查询的帧零喂入成本。
3. `_snap_items` 实体数组**不进 C++ 持久层**（修轮 v2 修订）：v1 曾以 COW 共享存入 C++ 成员 `snap_items`；修轮改为**每次查询按参数传入**（仍 COW 共享、零拷贝，但 C++ 侧零跨帧持有——对象生命周期窗口=单次同步调用，命中索引就地取实体写结果缓冲）。C++ 持久层只存几何（CSR 桶前缀/散布 + 位置 SoA）；`_nat_cells/_nat_pos` 脏标记保证查询前必然重喂。

**查询面（C++ 直返，零逐命中 GDScript 解析；修轮 v2 已修订——见 §9.3）：**

4. `query_circle_snap_nodes(items, pos, radius) -> Array[Node2D]`：C++ 扫描（id 暂存 std::vector，容量复用）→ 结果一次性落**成员类型化缓冲**（`set_typed(OBJECT,"Node2D")`）→ COW 共享直返；`items` 由调用方**每次调用传入**（修轮 v2：C++ 侧零持久对象引用——v1 的 items 成员存储已删除）。GDScript wrapper 一行转返——`SpaceGrid.query_circle_snap` 返回值契约不变（内部复用缓冲，跨查询持有须复制；`_query_buffer` 在原生路径不参与）。
5. `query_circle_snap_indices(pos, radius) -> PackedInt32Array` 纯几何诊断口（修轮 v2 改名/定型）：同源同序返回快照索引、不经手对象；T2.5 双口交叉验证逐位一致。
6. **逐位等价口径**（等价性测试实证）：
   - `reach = maxf(radius,0)+max_entity_radius` 全 double 域——实测锚：GDScript `maxf` 为 double 原生无 float32 往返；radius 参数绑定为 double（Variant FLOAT 原样透传）；
   - 覆盖格与 `_cells_in_range` 同式同序：`((pos.x ± reach) − origin.x)/128.0` double 域 → 向零截断（GDScript `int()` 语义）→ clampi（min>max 时 max 胜出）→ 行主序；
   - 距离精判 = `Vector2.distance_squared_to` 同式 `(sx−px)²+(sy−py)²` **float32** 域（SConstruct `-ffp-contract=off` 禁 FMA 收缩），升 double 与 reach_sq 比较；
   - 候选序 = 格行主序 × 桶内插入序（CSR 散布序天然=插入序）= GDScript 双循环序——返回序逐位一致。

**成本披露**（JSON bridge 段）：镜像随建 ≈ +42µs/rebuild（120 实体，rebuild off=449µs vs on=491µs，含冷启动噪声）；feed CSR 建桥 ≈ 67µs（每 rebuild 一次，首查时）；查询稳态零分配（结果缓冲容量复用）。

## 3. 开关门实现

```gdscript
static var NATIVE_QUERIES: bool = false          # 默认关=零扰动
static func native_available() -> bool           # ClassDB.class_exists + can_instantiate（判定缓存）
```
- 判定在 `configure()` **实例定型**（实例生存期内不翻转——镜像与桶序一致性依赖 rebuild/insert 期同步构建）；扩展缺失/加载失败 → `_native_obj` 恒 null、`_native_on` 恒 false，全路径自动回落 GDScript（T1.5 白盒注入 `_native_state=0` 实证回退分支）。
- 加载机制按工具链文档 §5：`.gdextension`（`repo/native/fission_space_grid.gdextension`，entry `fission_space_grid_library_init`，compat 4.3）→ 编辑器扫描 → `.godot/extension_list.cfg`（已实证生成）。**新环境/CI 首跑前必须过一次编辑器扫描**，否则静默不加载（门开也自动回落，不崩）。
- .gdextension 注册了 windows debug/template_debug/release/template_release + android template_debug 五键；android.release 键未注册（本轮只编译验证 .so，真机出包轮随 gradle 链补）——缺失键的安全面=导出后 native_available()=false 自动回落。

## 6. 过程坑（后来者直接抄）

1. **C++ 空结果也必须返回类型化缓冲**：返回裸 `Array()` 会让 `SpaceGrid.query_circle_snap` 的 typed return 对**每次空查询**抛 SCRIPT ERROR（I/O 计入耗时 → on 臂读数恶化三个数量级）——空路径 `resize(0)+return 成员缓冲` 修复。锚：`probe_r239_native.json` 前次读数与本次对比。
2. **set_typed 后 resize 保型、operator= 会清型**：类型化成员缓冲只在 configure（空+未共享）设型一次，后续仅 resize/写值。
3. **本轮引入并已修复的自伤**：一次编辑误删非空路径 `resize(m)` 导致 OOB 写 segfault（`_crash_diag.log` 已删）；最小复现探针定位后修复——教训：**直返缓冲的 fill 前必须 resize 到精确尺寸**（等价性套件 T1.7/T2.4 已把"空/非空返回类型化"纳入回归面防复发）。
4. 复现命令（其余照工具链文档 §8）：

## 9. 修轮 v2：真实负载崩溃根因定位与修复（2026-10-07 晚）

### 9.1 现象与复现

- on 态全量电池 4 套件 **0xC0000005 访问违例**：auto_idle（F 全链 soak 段）、pkg5、r187_rework、r235_quickwins（④ 4b 合并查询等价段——真弹 fast/slow 两臂驱动）。
- 单跑复现（临时翻真，v1 dll）：`... --headless --path repo -s tests/runner/test_r235_quickwins.gd` → **EXIT=139**；日志定格在 ④"slow 臂全查同计数同伤害"PASS 之后（下一段=释放敌 + `enemy_grid.rebuild([])` 空网格 + 弹体继续 tick）。
- r239_native 新增 T6 复现面（先于修复复现、修复后转绿）：旧 dll 下 `T6.1a PASS`（非空快照首查命中）→ `T6.1b PASS`（释放后重喂新快照）→ **T6.1c（空 rebuild 后同一网格再查询）崩**（两次独立复现 EXIT=139）；真 GameLoop 版 T6.2 同构。
- 崩溃 backtrace（`batt_r215_logs/r235_quickwins.log`、本轮回放日志）为 "no debug info in PE/COFF executable"，无法符号化——根因由读码 + 判别实验 + 最小复现三重证据链定位（下节）。本轮全部复现/回归日志留存工作区根 `_r239fix_logs/`（repro_*_old*=旧 dll 崩溃锚；fix_*/final_*=修复后）。

### 9.2 根因（证据链）

1. **直接缺陷**（`space_grid_native.cpp` v1 `feed_snapshot`）：空喂（n<=0）**早退时不复位 `bucket_off`**（CSR 桶前缀仍为上一份快照的计数），而 `bucket_flat`/`snap_x`/`snap_y` 已清空、`snap_items` 已被替换为刚喂入的空数组。
2. **真实负载必现路径**：敌全灭/回池 → 下一帧 `rebuild([])`（镜像清空、置脏）→ 弹体照常 `query_circle_snap`（④ 相位每弹每 tick 的接触预检/全查）→ 空喂 → 查询按**陈旧前缀**扫描 `k ∈ [off[c], off[c+1])` → `bucket_flat[k]` 读到已清空容器的陈旧索引 → `snap_items[i]`/`snap_x[i]` **越界读**（空数组数据指针解引用/脏 Variant）→ 访问违例。
3. **判别实验（排除"裸指针悬垂直接解引用"）**：T6.1b——非空喂 → **释放**原实体 → 重喂含新实体的快照 → 查询：PASS（命中新实体、无崩溃）。若是"C++ 存 Object* 且释放后解引用"，该用例即应崩；实证触发点确为**空喂之后的陈旧 CSR 扫描**。
4. 该缺陷在 v1 手工夹具（r239_native 20/20）不可见的原因：夹具的"空网格"实例从未先喂入非空快照（`bucket_off` 全零→扫描空集），而真实负载必然经历"有敌→无敌→继续查询"。

### 9.3 修法（v2 定稿）

| # | 改动 | 说明 |
|---|---|---|
| 1 | `feed_snapshot` 空喂/失配同样**全量复位桶前缀** | CSR 不变量恒成立：`bucket_off` 恒为当前快照完整前缀；`bucket_flat` 改**精确尺寸**（有效条目数）⇒ 不变量 `bucket_off.back() == bucket_flat.size()` 可校验 |
| 2 | 查询入口**不变量闸** | `cols/rows>0 ∧ off.size()==cols*rows+1 ∧ off.back()==flat.size() ∧ snap_x.size()==snap_y.size()`；任一破坏→返回空（绝不产出脏数据/越界读） |
| 3 | **C++ 零持久对象引用**（嫌疑#1 一并归零） | 删除 v1 的 `Array snap_items` 成员；实体数组改**每次查询按参数传入**（COW 共享、零拷贝；生命周期窗口=单次同步调用），命中索引就地取实体写成员类型化缓冲直返；尺寸护栏 `items.size()==快照条目数` 不符即返回空（越界面归零） |
| 4 | 纯几何诊断口定型 | `query_circle_snap_indices(pos,radius)->PackedInt32Array`（与 nodes 口共用 `_collect_hits` 同源同序、不经手对象）；T2.5 双口交叉逐位 |
| 5 | 溢出护栏 | `configure` 对 `cols*rows` 超 int32 域（不可能的生产配置）降级为空网格 |
| 6 | 桥接段同步 | `feed_snapshot(cells,pos)`（两参）+ `query_circle_snap_nodes(items,pos,radius)`（三参）；GDScript 公开面（`query_circle_snap`）与返回值契约不变 |

**备选方案实测披露（为何不采用"索引返回 + GDScript 映射"）**：该方案（C++ 返回 `PackedInt32Array`、GDScript 逐命中映射回 `_snap_items`）实测 on 臂 **1.94µs/查询、仅 2.10×（<3× 门）**——聚簇臂约 9.1 命中/查询，逐命中映射过路成本 ≈94ns（≈0.86µs/查询）。因不满足桌面 ≥3× 判据，改用上表 #3（C++ 侧按索引重建类型化 Array、items 每次传入不持久持有），A/B 回到 3.73×（§9.4）。两版实现均实测过（日志在案）。

### 9.6 复现用例（r239_native T6，修复后为防复发回归面）

### 9.8 残余风险与交接

- **残余风险①**：快照内**已释放实体**的结果项口径（`items[idx]` 为已释放对象）与 off 路径 GDScript `_query_buffer.append(_snap_items[idx])` 同款暴露面——本轮未改变、未新增（命中链消费端既有 `is_instance_valid`/dead 短路兜底）。
- **残余风险②**：真机 arm64 等价/性能仍待出包轮对拍（同 §7 风险②）。
- **翻开时机**：`NATIVE_QUERIES` 终态保持 **false**（fail-safe），由主控决定；T1.1 断言仍为"默认关"，翻开时需同步该断言 + 重跑本 §9.5 全表。
