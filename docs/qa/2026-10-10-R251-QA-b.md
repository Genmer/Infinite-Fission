## 3. 发现（findings）

### QA乙-1（中）首遇卡「暂停冻结」失守：LEVEL_UP/PAUSED 期间卡片照常倒计时、队列照常轮播，选卡窗被叠加轮播

- **位置**：`scripts/ui/first_encounter_card_ui.gd:57-66`（`_process` 计时）＋ `scripts/loop/game_loop.gd:214`（`process_mode = PROCESS_MODE_ALWAYS`）
- **期望**（设计 §3.3 与 UI 自注 `first_encounter_card_ui.gd:7`、`:58` 明文）：「PROCESS_MODE 默认 INHERIT——LEVEL_UP 暂停期计时不推进，队列不丢、恢复续播」；即选卡窗/暂停期间卡片不应消散、队列不应推进。
- **实际**：卡 UI 未显式设 process_mode（INHERIT=0），但其父链 GameLoop 为 ALWAYS（=3，`game_loop.gd:214`），INHERIT 传导后暂停期 `can_process()==true`，`_process` 照跑：
  1. `tree.paused==true`（LEVEL_UP 已生效）下 12 帧内 `ui._life` 0 → 0.139（照走）；
  2. PAUSED 态同象（life 0 → 0.076）；
  3. 玩家可见终局：LEVEL_UP 暂停期内把卡置 4.49s → 暂停期内到点**自动消散**，0.25s 间隔后队列下一张**照常弹出**——首遇卡（层 50）叠在选卡窗（层 1）之上轮播。
- **影响**：新档首局最常见——开局首发武器卡 + 首批敌卡尚未播完即迎首次升级，整个选卡期间卡片在玩家头顶轮播排干队列，违背「读卡窗在遭遇前/恢复续播」的设计意图；无功能与数据危害（卡面全 IGNORE 不挡选卡操作）。
- **复现步骤**：新档开局（清 `codex_first_met`）→ 进入战斗触发任一首遇卡 → 立刻吃经验触发升级选卡窗 → 观察顶部卡 4.5s 后自行消散并续播队列下一张（`tree.paused==true` 全程）。
- **探针证据**：`_qa_r251_b_probe5.log` `Q5c/Q5d/Q5e` 三行（Q5e 判据 PASS 即「暂停期队列照走」的实证；Q5c/Q5d 为契约断言 FAIL）。3 次复跑（probe3/4/5）结果一致。
- **建议方向**（供实施员参考，不在本岗权限内）：给 `FirstEncounterCardUI._ready` 显式设 `process_mode = PROCESS_MODE_PAUSABLE`（脱离父链 ALWAYS 传导），一处改动即可恢复 §3.3 契约；改后需回归 C7（手动 `_process` 驱动断言不受影响）。

### QA乙-2（低）武器上架口缺「空文案守卫」，三域三口纪律不一致（当前零影响）

- **位置**：`scripts/loop/game_loop.gd:2007-2015`（`_announce_weapon_first_shelf` 无 `weapon_note` 空串守卫）
- **现状**：敌口（`enemy_spawner.gd:89` `not note.is_empty() and …`）与获取回退口（`player.gd:896` 同款守卫）都有空文案防护，唯独上架口没有——若未来新增武器漏配 `weapon_note`，上架即弹**空正文卡**。
- **当前实测**：13 把武器 note 全覆盖（2.7 节），**今日零影响**；仅登记为健壮性观察，不阻塞验收。
- **建议方向**：上架口补同款 `not note.is_empty()` 守卫（一行），或在新增武器流程加 note 覆盖检查。
