## 总评

**不建议以现状出包：本批两把刀之一「拒绝可见化」在真机上完全失效（H1——横幅被不透明菜单底色整层盖住，玩家永远看不见），修复成本约一行。** 另一把刀「事件定罪链」骨架成立：七事件+状态迁移行对 R254-2 嫌疑面五假说中四类可定罪、一类（UI 层吞 tap）只能靠「无事件」反推（M2），且非法迁移拒绝不入环留下一个「start_run 行后无状态行」的二义缺口（M1），240 行共享环下事件约 4 分钟即被 1Hz 性能行冲走（M3）。**最影响体验的一件事**：用户下次复发「点出发没反应」时，本批承诺的「当场告知解锁缺口」横幅不会出现——症状与修前完全相同，等于这半个批次白做。

## 定罪链推演（评审维度 1 · 假说×事件矩阵）

| 复发假说 | 现有事件能否定罪 | 判读形态 |
|---|---|---|
| a) 解锁门拒（存档档位键错位） | **能** | 「出发拒绝：map=… 难度=… 未解锁（需先通关 X·Y）」一行即定罪；含上一关名+难度，正是 R254 嫌疑 a 的取证键 |
| b) 祝福池空直达但 start_run 前崩 | **能** | 「祝福池空（档 N）」→「start_run map=…」→「状态 1→2」三连；链断在哪一行、哪一环崩清清楚楚 |
| c) 面板弹了但渲染失败（确认键点不到） | **能** | 「祝福面板弹：池 N 项 · 档 N · map=X」后跟反复「出发二次（模态期）… 采用=true」而无「祝福确认」——R254-2 主嫌的自画像 |
| d) 瞬死后 GAME_OVER 自动回菜单 | **能** | 「start_run」+「状态 1→2」+ P 行性能样 +「状态 2→5」+「状态 5→1」时序即证「其实进了局又死出」；配合 probe 的首伤→死亡时间戳 |
| e) 二次出发被 pending 闸吞 | **能** | 「出发二次（模态期）map=… 采用=…」直证 tap 到达且被闸接住（R254 自愈后此路径还应跟随面板重开） |
| f) tap 被 UI 罩层/命中测试吞（R254 模态 STOP dim 残留等） | **不能直接定罪** | 导出呈「无事件」——只能反推 tap 未达 GameLoop，无法区分「罩层吞了」「没点中」「菜单假死」（M2） |

补充缺口：start_run 行发出后若 change_state(PLAYING) 被仲裁拒（真机状态卡在非 MENU），与「start_run 中途脚本错误崩」的链形态完全同构（M1）。

## 问题清单

### H1（high）可见化横幅被不透明菜单底盖住——flash_hint 整刀失效，B20 测不到
- **位置**：`scripts/ui/menu_screen.gd:239-248`（MenuHint 首个 add_child）vs `:251-256`（MenuBg 全屏不透明 ColorRect 后挂）；注释 `:237` 自称「挂 _root 尾部=盖一切菜单内容」——代码挂的是**头部**，注释与实现相反。
- **现象**：Godot CanvasItem 按兄弟树序绘制，后挂者在上层。MenuHint 是 `_root` 第 0 子，其上依次盖全屏不透明底色（#eef3ff，alpha=1）、云层、logo、按钮、面板……玩家在任何状态下都看不到横幅。拒绝路径（`_on_map_pick` :713-716 先关面板再 emit → game_loop :1848 flash_hint）的时序设计本身是对的，被 z 序一笔勾销。
- **测试盲区根因**：B20（r252_blessing_cases.gd:696-702）断言 `_hint_label.visible`——Control 的 visible **标志位**为 true，与实际是否被画出来无关，测试照样全绿。QA 功能面同构盲区。
- **建议**：`_ready()` 内 `_build_panel()` 之后补 `_hint_label.move_to_front()`（不能只挪 `_build_ui` 末尾——`_build_lobby`/`_build_panel` 随后会再挂子把它压回去）；B20 补绘制序断言（如 `_hint_label.get_index() >= _root.get_child_count() - 1`）。一行修复+一条断言，本批半条命在这。

### M1（medium）非法迁移拒绝不入环——「start_run 行有了但没进局」二义
- **位置**：`scripts/loop/game_loop.gd:1036-1043`（拒绝分支仅 rejected_transitions++ + 5s 节流 push_warning）。
- **现象**：`_finish_menu_start` :1862 **先**发「start_run map=…」**再**调 start_run()；start_run :1628 首行 change_state(PLAYING) 若被拒（真机状态卡 GAME_OVER/LEVEL_UP 等），链停在 start_run 行、无「状态 1→2」——与「demon 波表缺失致 start_run 中途崩」（R257 嫌疑面）形态完全同构。push_warning 只进 logcat，用户导出的 diag 里没有，真机无 logcat 条件下两假说不可分。
- **建议**：拒绝分支补一行 `DebugStats.event("迁移拒绝 %d→%d（计数 %d）")`（节流照旧；事件本身低频）。定罪链最后一个二义缺口。

### M2（medium）事件链不覆盖 UI 按钮层——「tap 被吞」假说只能靠空白反推
- **位置**：`scripts/ui/menu_screen.gd:713-716`（_on_map_pick 仅关面板+emit，无事件）；`:526-527` 主出发钮同。
- **现象**：若真机病灶是 R254 引入的祝福 dim（MOUSE_FILTER_STOP）异常残留吞点击、或任何罩层/命中测试失败，导出日志呈「无事件」。这固然指向 UI 层，但无法证明 tap 确实发生过（vs 没点中/菜单假死）——恰是「桌面全链无法复现」类病灶最需要正向证据的地方。
- **建议**：_on_map_pick 在 emit 前补 `DebugStats.event("选关出发钮 map=%s 难度=%d")`，把定罪链起点从 GameLoop 入口前移到按钮层。一行，假说 f 从「反推」变「直证」。

### M3（medium）240 行共享环下事件行 ~4 分钟被性能行冲走——延迟导出即丢证
- **位置**：`autoload/debug_stats.gd:231-235`（event 与 1Hz 采样行共 `_diag_lines`；容量默认 240，meta_manager.gd:300；diag_log 默认 true :298，MENU 态也每秒采一行）。
- **现象**：定罪窗≈240 秒。反复重试的复发（每次重试重新发事件）尚可定罪；一次性失败后用户先折腾几分钟再找到「导出诊断日志」按钮，事件行已被性能行环形覆盖。本批全部价值押在「下次复发导出定罪」上，这个窗口太脆。
- **建议**（按性价比）：事件行独立小环（如 120 行 event-only，`diag_export` 先拼事件段再拼性能尾段，头部披露各自条数）；或事件行 sticky 不参与覆盖写。顺带：event() 绕过 diag_log 采样门与 calib 先例一致，是对的（diag_log 关掉时事件仍留痕、且环不被性能行稀释）——建议在导出头口径声明里补一句。

### M4（medium）tracker R257 节仅需求表——实现注记/门禁/测试资产零登记

- **现象**：本批已落的 event()/flash_hint/七事件清单/B20/B21/probe 均未登记。若属收口时序（评审先行、登记后补）不算缺陷，但出包前必须补齐——含 H1 修复记录与「拒绝可见化曾整刀失效」的诚实登记。
