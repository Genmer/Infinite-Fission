## 概述

把真机深载从「模拟预算塞不进 60Hz 步长 → 渲染被物理帧拖垮（fps 14-25、模拟率随帧率
滑落」改为「模拟恒 30Hz（33.3ms 步长，实测管线 33ms 刚好塞下）+ 渲染独立跑 60-120fps
+ 自建插值层抹平 30Hz 位置阶梯」，同时按 30Hz 口径重标结算预算帽与派发/吸收侧全部
**帧数语义参数**（96/192 每步 + 派发 96/步 + 吸收 48/步），使伤害供给 ≥ 需求且反馈
链路不饿死，兑现 vc37 深载一半命中被弃（弃N 2600/s）的伤害欠账。
**T8 实测修正（R4）：「刚好塞下」只在帽 192 深载以下的负载段成立——深载段步耗
overrun 的形态与分诊见决策1b，交换包终裁归 vc38 用户试玩。**

## 项目背景（实测与代码事实，设计算术基础）

### 性能实测（已定案采信，不重新推导）

- 真机深载每步模拟管线 ~33ms：结算轴 8-10ms + 弹段 7-10ms + 长尾 17-19ms（R228 归因，
  用户确认）。60Hz 步长预算 16.6ms 塞不下 → fps 14-25；30Hz 步长 33.3ms **刚好塞下但
  贴边（零余量，需求继续增长会破）**——**R4 修正：T8 桌面 B 臂（30Hz 帽192 敌120
  深载）步耗 p50=51.84ms 已破此预算，深载 overrun 形态见决策1b**。
- 真机现状（vc37 日志 + meta_manager.gd:515-525 实读）：mobile 门内
  `Engine.physics_ticks_per_second=60`（R204）+ `Engine.max_physics_steps_per_frame=1`
  （帽1，R218 刀B）+ fps_cap。桌面/headless：project.godot `physics_ticks_per_second=120`，
  测试手动驱动 `_physics_process(1/60)` 全按 DT60 口径（电池 114 套件基线）。
- 帽1 下**模拟率与物理服务器有效频率同跌至 min(fps,60)**：vc37 深载段「模14-22」≈
  fps——渲染被物理帧锁死，游戏变慢动作；物理服务器（Area2D 同步）深载实际也只跑
  14-25Hz，**不是 60Hz**（事实修正B：凡涉及「物理服务器成本」的对比，参照系都是
  14-25Hz 而非 60Hz）。
- 结算需求（提交量 = 结N+顺+弃）：典型深载 4500-5500/s；vc37 峰值行（0:31）1440+4420
  +2600 = **8460/s**。现供给 = 帽96 × 模拟率 ≈ 96×25 ≈ 2400/s，一半以上命中弃/顺。
- 真机单结实测（vc37 结µs/结N 反推）：58-99µs/结（与 R232 报告「37-99µs」口径吻合；
  行内结µs 键现打印秒累计 µs——见 §捎带修复）。
- 需求随构筑强度增长：弃N vc36 1554 → vc37 2600。
- 渲染轴非瓶颈：暂停/选卡帧 fps120（vc37 0:42 行）；dc 350-1000。
- **T8 步长探针（R4，docs/qa/probe_r233_stepsize_2026-10-05.json）**：桌面 B 臂

  C 臂探针在跑、vc38 实测定。

## 核心循环（性能视角）

本刀不改玩法核心循环（割草-构筑-成长），改的是它的**承载循环**：

```
渲染帧 60-120fps（独立）── 插值层读双缓冲位置 + alpha → 平滑画面
      │ 每积满 33.3ms 触发一步
      ▼
模拟步 30Hz 恒定（33.3ms 预算 ≥ 实测 33ms 管线）
      ├─ 结算预算 96/192 每步 → 供给 2880-5760/s ≈ 需求 → 弃N→≈0
      ├─ 派发帽 96/步 + 吸收帽 48/步 → 反馈链（跳字/HUD/收割）秒口径平价不饿死得更糟
      └─ 帧率不再被物理帧拖垮 → PerfGovernor/特效档不再钉死深谷
```

为什么有效（目标-反馈-成长闭环）：稳定性是手感的底座——玩家操作 → 恒定 30Hz 模拟
响应 + 稳定 60+fps 画面反馈 → 构筑成长不再被帧率塌方惩罚。**第一验收锚定中载段
（AC-1a 硬门：fps p50≥40 / 模N=30 / 步耗 p95≤34ms——②路线主战场）；深载段步耗
overrun 是设计内降级形态（决策1b），其「fps↓ ↔ 流速↑+伤害全额兑现」交换包归 vc38
用户试玩终裁（AC-V⑤），不在纸面预裁定**。

## 机制细节

### 决策1：降频机制选型 —— 定案方案A（Engine.physics_ticks_per_second=30）

| 维度 | 方案A：引擎物理 30Hz | 方案B：引擎 60Hz + game_loop 自管 30Hz 累积器 |
|---|---|---|
| 挂点 | meta_manager.gd:516 一行 60→30（R204 mobile 门同款先例） | game_loop 帧序重构为两层（外 60Hz 回调+内步进闸），改动面大 |
| 主循环 | 唯一消费者 game_loop 自动 30Hz（已核实零其他消费者） | 同样 30Hz，但需重排 PLAYING 与模态分支的步进闸 |
| 物理服务器 | **目标态封顶 30Hz**（见下「成本账」修正口径） | 目标态付至渲染率（≤60Hz）——fps≥30 后比 A 多付一倍 |
| Area2D 语义 | 接触信号采样 30Hz：重叠起检延迟 +16ms 级（最坏），伤害期望守恒（见下） | 零变化 |
| Timer/Tween | 已核实全部非物理帧依赖，两案均零影响 | 同 |
| headless 电池 | 手动驱动 `_physics_process(1/60)` 不读 Engine 设置 → **114 套件零扰动** | 每次调用≠一步 → 「每调用=一步」假设全体破坏，须 sim_dt_override 分叉双路径（测试矩阵翻倍） |
| 降频生效可观测 | `模N`/`p` 键现成直读 30/30 | 模N 仍读引擎物理帧（60）需另立步数键 |
| 回退 | 开关联动单点（见决策4；回退门分诊=决策1b） | 累积器+帽+相位多处联动，回退面宽 |

**定案：方案A。** 决定性理由：①影响面闭合（唯一 `_physics_process` 消费者 + 零物理帧
Timer/await/Tween，已全仓核实）；②headless 电池天然零扰动；③目标态（fps≥30）物理服务器
频率封顶 30Hz，方案B 要付到 60Hz。方案B 唯一实质优势（Area2D 保持 60Hz 采样）经语义
核查非必需——接触伤害量是固定值+秒基无敌帧节流，30Hz 采样下每秒伤害期望不变，仅
「重叠起检」最坏 +16ms，与全游戏 30Hz 时序一致、敌我同频公平。

**物理服务器成本账（R2 事实修正B 后口径）**：现状深载物理服务器有效频率 =
min(fps,60) = 14-25Hz（帽1），**不是 60Hz**——30Hz 解耦后每秒物理服务器工作量从
14-25Hz 升到恒 30Hz（有界小增，每步成本不变、含在 33ms 实测管线内）。「60→30 减半」
只发生在两处且都不是深载收益：轻载帧（现状 60Hz→30Hz，本就有余量）与方案对比
（目标态 A=30Hz vs B≤60Hz）。本设计不把「物理服务器省一半」计入收益账。

**Area2D 30Hz 影响定案（方案A 披露项）**：
- 敌接触伤害（R202 信号驱动缓存）：`area_entered/exited` 派发频率跟物理 tick（深载现状
  14-25Hz → 恒 30Hz，实为**采样更稳**而非减半）；`_contact_player` 旗的建立/清除相对
  60Hz 标称最坏 +16ms；伤害结算仍在敌 tick（30Hz）读旗——每秒结算次数期望不变
  （无敌帧节流主导），起伤/停伤时点 ±16ms 级，公平性敌我同频保持。
- 玩家命中盒（Area2D 低频例外）：同上，仅被敌弹/接触查询消费的位读不受影响（那些是
  逐弹距离判定，不走物理服务器）。
- 变体C（A + backlog #7 敌 Area2D 迁 SpaceGrid 提前做）：**不做**——backlog #7 是独立刀，
  捎带=范围蔓延；本刀披露 Area2D 采样语义即可。

**步长边界与慢动作语义**：帽1（max_physics_steps_per_frame=1）保持不动。渲染 fps≥30 且
步耗 ≤33.3ms 时模拟率恒 30（模N=30 稳态）；渲染 fps<30 或步耗超步长时模拟率=fps
（帽1 防螺旋，慢动作保护语义原样——深载 overrun 段的完整形态定义见决策1b）。
`GAME_DELTA_CLAMP_S=0.25` 在固定步长下不触发。顿帧（time_scale 0.05）：raw=1/30，语义不变，
仅顿帧期模拟粒度 1.67ms/步（原 0.83ms），顿帧是表现效果不受损。

### 决策1b：深载 overrun 形态定义与分诊改写（R4 补写，T8 实测定案）

**实测背景**（docs/qa/probe_r233_stepsize_2026-10-05.json）：桌面 B 臂（30Hz 帽192
敌120 深载）步耗 p50=**51.84ms > 33.3ms 步长预算**；真机投影（桌面→真机放大系数）
**62-114ms/步**。「33.3ms 刚好塞下」在帽 192 深载档不成立——本节定义 overrun 形态
并改写回退分诊（覆盖前文一切「步耗超标 → 回退 SIM_30HZ」口径）。

**overrun 形态定义**：步耗 > 步长（33.3ms）时，帽1 固定步长语义下时间累计器每渲染帧
欠账、每渲染帧恰带一步 → **fps = 模N = 1000/(步耗+渲染)**——深载段渲染与模拟**依然
耦合**；渲染解耦收益只在「步耗 ≤33.3ms」负载段（中载及以下）成立。

**深载段实际形态（T8 投影）**：
- fps = 模N ≈ **8-14**；
- 游戏流速 0.29-0.53×（现状深载 0.23-0.37×——同帧率下慢动作约**减半**，时间账更顺）；
- 弃N ≈ **0**（帽 192 供给在深载兑现——伤害全额落账）；
- 输入最坏延迟 62-114ms。

**深载交换包 = fps↓30-40% ↔ 流速↑（慢动作减半）+ 伤害全额兑现**。最终裁定归 vc38
真机 AC-V（用户试玩，见⑤），**不在纸面预裁定**。

**分诊改写（R4 定案）**：
1. **回退门仅由中载段硬门失败触发**（AC-1a）——SIM_30HZ 是 boot 级全局开关，深载段
   触发回退=放弃②路线全部收益（含中载段的解耦收益与弃N 兑现），出口比深载降级形态
   更差；
2. **深载段步耗超标 = 设计内降级形态**（非缺陷、非回退信号），走 AC-V 用户裁定；
3. 模N<30 读数判读口径：**中载段出现** = 硬门失败候选（回退分诊入口）；**深载段出现**
   = overrun 形态本身（AC-1b 披露对账项，预期值 8-14）。

### 决策2：四处「隔帧/相位」节流面随 SIM_30HZ 短路（必做）

「60Hz 物理帧内隔帧驱动=30Hz 效果」的实现，在物理帧本身降到 30Hz 后会把对应面打到
**15Hz**（过糙，观感劣化）。全部随 SIM_30HZ 短路直驱（每步以 1/30 delta 驱动）：

1. `_ui_subtick_left`（跳字 mobile 半频，game_loop.gd:160/:2756-2762）；
2. `_fx_subtick_left`（元素特效层半频，:161/:559-565）；
3. `_shard_subtick_left`（磁吸碎片半频，:80/:613-620）；
4. **orbit_field `_redraw_ctr % 2` 重绘节流（orbit_field.gd:245-250，R2 坐实补入）**：
   R188 档0 的 120Hz tick→60Hz 重绘节流。30Hz 下不短路则环绕武器 `_draw()` 制视觉
   （公转环/球体）只有 15Hz——**插值层只覆写实体 global_position，救不了 `_draw()`
   自绘内容**，必须每 tick 重绘（=30Hz，与现状 mobile 实效等价）。

开关回退 60Hz 时四处相位/节流逻辑原样恢复。分析阶段仍须以 `subtick|_left -= 1|隔帧|
% 2` 模式全仓复扫防第五处（开放问题#8）。

### 决策3：插值层（自建，纯表现，_process 通道）

#### 3.1 双缓冲与写入时序（池化零分配实现）

每个被插值实体增加两个 Vector2 成员（池化节点成员字段，无 GC 压力）：`_ip_prev` / `_ip_curr`。
`global_position` 定性为「显示缓存」，模拟真位永远以 `_ip_curr` 为准：

```
模拟步开头（_physics_process 帧入口，_maybe_trim_pools 之后、pipeline.begin_frame 之前）：
    恢复遍历：active 实体 global_position = _ip_curr   ← 抵消渲染帧覆写，防污染 ②④⑤ 段读位
    （playable 帧 PLAYING 分支才需要；恢复与快照遍历源见 3.4）
模拟步末尾（EventBus.end_frame 之后）：
    快照遍历：active 实体 _ip_prev = _ip_curr; _ip_curr = global_position
渲染帧（GameLoop 新增 _process，纯表现通道）：
    alpha = clamp(距上次模拟步的耗时 / (1/30), 0, 1)
    active 实体 global_position = _ip_prev + (_ip_curr - _ip_prev) * alpha
```

- alpha 计时：`_process(delta)` 内累计 `_alpha_t += delta`；每渲染帧检查
  `Engine.get_physics_frames()` 是否较上帧推进（本刀后正常态每渲染帧 0 或 1 步），推进则
  `_alpha_t` 以本渲染帧为步进点重置基准（精度=渲染帧粒度，120fps 下插值 4 档/步，
  60fps 2 档/步——远优于 30Hz 直排的 1 档）。**深载 overrun 段（决策1b）每渲染帧恰带
  一步，alpha 常驻低位（渲染帧间隔 ≪ 步长）——插值退化为亚步直排，无撕裂（写入位
  始终 ∈ [prev,curr] 包络），平滑收益归零属预期**。Engine.get_physics_interpolation_fraction
  4.3 不存在，不使用。
- **开关关（SIM_30HZ=false）时 `_process` 首行谓词直返零写**（R2 修正：原稿「直通写
  curr」废弃）——现状本无 `_process` 写点，直通写是零收益的每帧遍历（深载 ~780 实体 ×
  120fps），且引入回池/树外实体的边角暴露面；首行直返使 headless 零扰动论证更干净
  （headless 直驱下 _process 脉冲有无都不产生写点）。
- 暂停/选卡（tree.paused）：战斗实体不 tick → prev=curr 冻结 → 渲染帧写 curr 直通
  （插值自然退化为静止）；磁吸碎片模态期被 raw 驱动照常快照+插值。MENU/GAME_OVER 无
  战斗实体，遍历空转。
- 恢复遍历挂点必须在帧序 ②（player.tick 读自身位）与 ④（网格 rebuild 读敌位）之前
  ——即物理帧入口顶部，一次遍历覆盖全部读点。
- 快照遍历挂帧序最末：敌 tick 内击退/闪现、玩家瞬移（player.gd:787）等一切写位都被
  帧末统一快照收编。

#### 3.2 插值分级（哪些插、哪些不插）

| 层级 | 实体 | 数量级（深载） | 定案 | 依据 |
|---|---|---|---|---|
| P0 | 玩家 | 1 | **插** | 手感主体，30Hz 直排在 120Hz 屏不可接受 |
| P0 | 敌（含 Boss） | 100-120 | **插** | 大实体肉眼最显；敌子节点（贴图/telegraph）随父级 transform 自动平滑 |
| P0 | 玩家弹+敌弹（双弹池） | 200-420 | **插** | 弹是画面主体；120Hz 屏上 30Hz 直排=可见跳格（每步 10-33px）。「拖尾/运动模糊掩盖」不采：贴图烘焙+分桶合批体系下加拖尾=新增渲染面，成本不明且破批风险，插值已覆盖需求 |
| P0 | XP 碎片/掉落物 | ≤240 | **插** | 磁吸飞行是收割演出焦点，低速但路径长 |
| 不插 | 跳字 | ~24 在场 | 不插 | 本就 30Hz 驱动（mobile 半频→直驱），观感已验（R206/R212） |
| 不插 | 粒子/元素特效层 | — | 不插 | 低频驱动/短命对象，插值收益低 |
| 不插 | 激光/轨道/镜像 | ≤8 | 不插 | tick 内从武器参数整段重算线段/角度，非增量位移，插值会撕裂判定与表现。orbit_field 视觉靠决策2-④每步重绘兜平滑，不靠插值 |
| 不插 | 相机震屏 | 1 | 不插（开放问题#6） | camera.offset 在 ⑧ 段 30Hz 写入；震屏是高频噪声，30Hz 更新观感待真机裁定 |

像素风注意：项目渲染位置本就未做整数 snap（`_sync_visual` 仅量化 scale），插值写亚像素
位与现状一致，无新增模糊。

#### 3.3 成本预算与可观测（防插值层自己变瓶颈）

- 写入成本量级：深载 ~600 实体 × global_position 属性写 ~0.3-0.5µs ≈ 0.2-0.3ms/渲染帧；
  恢复+快照两遍 ≈ 0.3-0.6ms/模拟步。合计摊入 33.3ms 步长预算 <2%，但**贴边预算下必须
  可观测**：新增诊断键 `插µsN`（渲染帧插值写入的秒累计 µs÷采样窗→均值，1Hz 行行尾追加，
  既有子串逐位保持）。验收含插µs 上限（见 AC 表）。
- 遍历复用现有缓冲纪律（成员级 Array 复用，`_collect_enemy_bullets` 先例），零分配。

#### 3.4 遍历源与池化生命周期矩阵

- 遍历源（与 diag_counts/_collect_enemy_bullets 同源）：`_projectile_pool.active_projectiles()`
  + `_homing_pool.active_projectiles()` + `spawner.active` + `active_shards` + player。
- 池化矩阵（新套件逐条锁）：
  - spawn：`_ip_prev = _ip_curr = 出生位`（防从池内旧位/桶位飞入）；
  - release：不清（下任 spawn 重置覆盖）；弹桶 reparent（`_place_in_bucket`）在 spawn 期，
    与快照无交互；
  - 回收当步：渲染遍历只走 active，回收实体天然排除；
  - headless 直驱（无 _process 脉冲）：插值写入不跑（3.1 首行谓词）、恢复遍历幂等 →
    模拟位=显示位，既有 114 套件读数零漂移。

### 决策4：隧穿对策（30Hz 每步位移 ×2）

算术基础（R2 修正后，最坏弹速 979.2 px/s——W2/W6/W7 700-720 基速 × AFF_PROJ_SPD
×1.36 叠层档，weapon_base.gd:459-464 共用乘区；回旋刃 860 硬帽独立口径不吃乘区）：
30Hz 步长 = 979.2/30 = **32.64px**（回旋档 28.7px）。敌 hitbox_r 最小 12（E10
woodbird）、多数 14；弹 hitbox_radius 基础 6（size_mult 放大只增不減）。点检测不漏的
保守条件是步长 < 2×reach=36px（最小 reach=6+12=18px）：静止敌 32.64px 已贴 36px 上沿；
**对头 chase 敌（相对速度可至 ~1179px/s → 39.3px/步）已越过 36px——点检测真实可漏**
（60Hz 基线步长 ≤16.3px 有 2 倍+富余，故历史上无隧穿投诉）。**T8 B 臂实证（R4 引注）：
步长翻倍形态下实测需求 −25% / 击杀 −17%（probe_r233_stepsize_2026-10-05.json）——
漏检已可量测，swept 必要性从算术推定升级为探针级证据**（AC-5 场景矩阵对拍锁）。
结论：30Hz 下快弹×薄敌×对头组合存在确定性漏检窗口，swept 是**必要项**而非保险项。

定案：**查询膨胀 + 线段窄相（swept 圆）**，仅 SIM_30HZ 生效（60Hz 回退旁路=逐位旧行为）：

- 粗判膨胀：`_check_collision` / `_tick_fast_player` 预检的 `query_circle_snap` 查询半径
  由 `er` 改 `er + |velocity|·dt·0.5`（最大弹速档膨胀量 ≈16.3px，查询半径 6→22.3px；
  网格查询参数加大，成本≈0，候选集略增）。**两处都要膨胀**——pfast 预检非空才回落
  全查，预检不膨胀=快路径漏检。
- 窄相线段化：`_in_reach` 由「当前位置点距」改「**本步步前位→步末位** 位移线段到敌
  圆心距离 ≤ er+tr」（点-线段距离，一次投影+sqrt）。
- **prev 源=步前暂存，与插值缓冲彻底解耦（R2 修正：原稿「取 `_ip_prev`」废弃）**：
  `_ip_prev` 在快照语义下是 **N-2 步末位**（帧末快照 `_ip_prev=_ip_curr` 先执行，
  `_ip_curr` 才接收本步末位）——用它扫的是两步位移（≤65px），会造成跨帧重复命中，
  破坏 AC-5 守恒等价断言。改为 `_move` / `_tick_fast` / `_tick_fast_player` 运动执行前
  stash `global_position` 到弹侧成员暂存位（恢复遍历已保证此时 global_position=本步
  步前真位），swept 读该暂存位——两种开关态（插值开/关）与 headless 直驱下语义一致。
- 敌弹撞玩家（`_tick_fast` / `_check_player_hit` 点检测）：敌弹速 ≤560 → 步长 18.7px vs
  reach 22px 直径 44px，富余充足，**不动**（保持逐位）。回旋刃 ICD 接触：步长 28.7px vs
  reach 直径 40px，富余，不动。
- 等价口径：膨胀+swept 是检测超集（60Hz 下两者命中集相同；30Hz 下补上跨步命中）——
  「同轨迹 60Hz vs 30Hz+swept 命中集相等」是新套件断言（见 AC-5）。

### 决策5：手感/公平性补偿与回退开关

- 输入延迟算术：触摸事件即时入 `_drag_accum`（事件驱动），消费在 30Hz 模拟步 → 平均
  +8.3ms、最坏 +16.7ms（相对 60Hz 消费；**深载 overrun 段最坏 62-114ms——决策1b 披露，
  AC-V① 观察项**）。位移总量守恒（累计制）。**不做**渲染帧输入预位移补偿（过度工程；
  补偿面=玩家位与判定解耦，破坏「模拟真位单源」）。真机试玩裁定（观察清单见 AC-V）。
- 公平性：敌 AI、敌弹、接触判定全部同 30Hz——敌我相对时序等频，公平性结构不变；
  玩家躲弹判定窗从「60Hz 采样×敌弹步长」变「30Hz 采样×敌弹步长×2」，侧擦判定窗
  净变化 ≈0（敌弹速低、reach 富余，见决策4）。
- 回退开关（项目惯例：static var + 一键回退 + 联动派生，防半回退态；**触发分诊=决策1b**）：

```
static var SIM_30HZ_ENABLED := true     # 挂 game_loop（测试可注入 false）
生效门：mobile ∧ true（桌面/headless 恒 false=现状 60Hz 口径零扰动）
SIM_30HZ = true 时联动（五项同谓词，R3 计数统一——防 checklist 漏点）：
  ① meta_manager._apply_fps_cap：Engine.physics_ticks_per_second = 30（mobile 门内）
  ② 结算帽表：tier1 96 / tier2 192；SETTLE_STALE_FRAME = 6（见决策6）
  ③ 派发/吸收帧帽：DISPATCH_FRAME_CAP = 96/步、STALE_FRAME_WINDOW = 15 帧、
     MAGNET_ABSORB_PER_FRAME = 48/步（见决策6-R2 补）
  ④ 四处隔帧/相位节流短路（决策2）；swept 隧穿对策启用（决策4）
  ⑤ 插值层启用（_process 写点开）；false 时 _process 首行谓词直返零写（决策3.1）
SIM_30HZ = false 时：以上五项全部回到 60Hz 现状值——单开关全联动
```

- **不做自动回退**（PerfGovernor tier 与模拟频率解耦）：30Hz 是地板不是档位，自动在
  30/60 间摆动会造成帽语义/时序窗抖动，复杂度与收益不成比。用户面手动回退档（设置页
  「模拟频率 30/60」行）列为可选（P1），默认 30。
- 开关读取时点：`_apply_fps_cap` 在 Meta._ready 与 settings_changed 时调用；SIM_30HZ 为
  static var（进程级），boot 期一次定型，不做运行期热切（热切=步长边界处半帧混合，
  无消费者值得支持）。

### 决策6：结算/派发/吸收三类帧数语义参数的 30Hz 重标（R223 DPS 守恒红线内）

供给算术（用户拍板口径）：帽 × 步率。30Hz 下 tier2 96→**192** → 供给 5760/s > 典型需求
4500-5500/s → 弃N→≈0；tier1 48→**96** → 2880/s（tier1=低特效深谷档，供给低于典型需求，
深谷行仍顺延合并——守恒不弃，符合 tier1 降载初衷）。

**R2 补（放行条件#2）：派发与吸收侧联动，防「伤害兑现但反馈饿死」**——供给抬到
5760/s 后，若派发帽仍 48/步（=1440/s 派发上限），跳字/HUD/relic/gamefeel/sfx 五订阅者
只能见到 1/4 的结算事件，AC-2 的体感兑现不成立；吸收帽仍 24/步则 160 片回收从 0.12s
摊开变 0.23s。三参数与帽同谓词联动：

| 参数 | 现值（60Hz 口径） | 30Hz 重标 | 语义 |
|---|---|---|---|
| SETTLE_BUDGET_T1 / T2 | 48/96 每帧 | **96 / 192 每步** | 供给 2880/5760 per s |
| SETTLE_STALE_FRAME（结算顺延过期） | 12 帧（≈0.2s） | **6 帧（≈0.2s）** | 时间语义守恒（12帧@30Hz=0.4s 会把击杀后移体感翻倍） |
| DISPATCH_FRAME_CAP（派发帽，damage_pipeline.gd:279） | 48 条/帧（≈2880/s） | **96 条/步（≈2880/s）** | **R3 论证修正为「比例平价」**：每秒派发上限=60Hz 原口径（48×60），重标后反馈**不比现状更糟**。派发队列输入=结N（damage_pipeline.gd:850-859 `_broadcast` 每次成功结算入队一条）——典型深载稳态结N ≈ 需求 4500-5500/s = **150-183/步 > 96/步**，稳态亏空 54-87 条/步由派发顺延（dispatch_deferred）+15 帧过期窗诚实卸载（dispatch_stale_drop）兜底，与 60Hz 现状深载同形态（结N 1440-2600/s vs 实际派发 ≤48×fps）——「全量派发」不成立也不作为验收目标。**192 条/步（对齐 5760/s 供给）= vc38 条件触发，与帽 240 同族**（触发条件与披露见数值框架表注/开放问题#3-4/#9） |
| STALE_FRAME_WINDOW（派发顺延过期，:284） | 30 帧（≈0.5s） | **15 帧（≈0.5s）** | 时间语义守恒（30帧@30Hz=1.0s，跳字迟到 1 秒=时序无意义）；15 帧窗同时是派发亏空「有界卸载」的兜底（亏空最多积 0.5s 后丢弃，不无界增长） |
| MAGNET_ABSORB_PER_FRAME（吸收帽，game_loop.gd:1482） | 24 片/帧（≈1440/s） | **48 片/步（≈1440/s）** | 每秒吸收上限与 60Hz 口径对齐；160 片回收仍 ~0.12s 摊开（3-4 步），vc21 磁键尖峰口径不回退（单步 48 片 ×gain_xp 链 ≈ 60Hz 帧内 24 片 ×2，仍在 R214 实测安全带） |

- 帽值派生跟开关：`_settle_cap_now` 读 SIM_30HZ 生效位选帽表（96/192 vs 48/96），派发/
  吸收三参数同谓词——**禁止**任何一参数与开关脱钩（示例事故：回退 60Hz 后帽仍 192 =
  11520/s 供给，192×70µs=13.4ms 超 16.6ms 帧预算 80%，帧率崩；派发帽脱钩则反馈饿死）。
- **const 断言保护策略（R3 提入，源自分析报告 Q6）**：`SETTLE_BUDGET_T1/T2`、
  `SETTLE_STALE_FRAME`、`DISPATCH_FRAME_CAP`、`STALE_FRAME_WINDOW`、
  `MAGNET_ABSORB_PER_FRAME` 六个原 const **值一律不动**——既有 r223/r221 套件直断言这些
  常量值（48/96/12、48/30、24）；30Hz 档以**新增档位常量**（`*_30HZ` 后缀或选表）+
  选择器按 SIM_30HZ 取值实现。AC-3 电池兜底；提前写明此策略省一轮电池红。
- DPS 守恒论证：帽提高只减少顺延量，FIFO 同对合并/冲刷/强冲语义零改动；顺延占供给
  比例下降 → 期望伤害不变、实现率上升。**伤害数值/顺序逐位等价不适用本刀**（供给变化
  本身改变结N/顺/弃分布——这是设计目标），等价门禁改为「同供给 override 下逐位等价」
  （既有 r223/r232 套件用 settle_budget_override 注入即覆盖）。
- 诊断判读口径更新（诊断先行的惯例）：diag 头注「结N≈帽(48/96)×帧率」改
  「结N≈帽(96/192)×模N」；模N 预期值分段：中载及以下=30，深载 overrun 段=8-14
  （决策1b）。
- 真机标定计划：结µs 修复（决策8）落地后，vc38 单结 µs 正确口径 + 步耗读数是派发帽
  （96→192 条件触发）的终审依据；**结算帽 192 已主控定案（R4：T8 桌面步耗 FAIL 如实
  记档、进 T3，vc38 真机终审）——见数值框架表注**。

### 决策7：诊断口径（fps 稳定性量化 + 新键）

- **新增 1 键**：`插µsN`（渲染帧插值写入秒均值 µs，1Hz 行行尾追加在 结µs 之后，既有
  子串逐位保持；qa_r228_diagfreeze 尾锚正则同步迁移——R231/R232 先例）。落地先于插值
  层行为刀（插µs=0 期=开关关闭基线）。

### 决策8：捎带修复——结µs 双消费 bug（game_loop.gd:280/:294）

现状：`diag_counts` 内 `&"settles"` 键（:280 `_diag_settles_delta()`）先消费差分基线，
`:294 _diag_settle_us_per()` 内部再拉 `_diag_settles_delta()` → 第二次返回 0（基线已被
刷新）→ maxi(0,1)=1 → 结µs = 秒累计 µs ÷ 1 = **秒累计值**（vc37 行 5 位数量级实锤）。

键改读同一次差分结果（一次拉取双消费——顺序反转）；② `_diag_settle_us_delta` 与
`_diag_settles_delta` 合并为单函数一次拉取返回双值。诊断 only、真实链零改动；直调测试
「重复拉取增量=0」口径保持（首拉立基线语义不变）。独立提交、独立回退，先于 30Hz 行为
刀落地（vc38 需要正确的单结 µs 做帽标定对账）。

## 假设与开放问题（下游分析师重点看）

1. **R233 编号冲突披露**：R232 收口报告 §五曾预留 R233=「ctx 侧 typed 结构格式」立项

   （FULL 盲区 35%/袋重建 4.1µs）未被本刀消解，账面不动。

   拖累）。30Hz 解耦后中载段渲染 fps 上限=gl_compatibility 在对应 dc/o 下的真机能力，

   FAIL 记档进 T3、vc38 终审；备选 144/240 触发条件见分析报告 Q4 表）**；
