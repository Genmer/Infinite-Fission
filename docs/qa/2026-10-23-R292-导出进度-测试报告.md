## 缺陷清单

### D1【low】连续两次完整导出：同秒内文件名冲突，第二次覆盖第一次（R205 既有，非 R292 引入）

- 复现步骤：
  1. 菜单态按下「导出日志」，帧泵至对话框弹出（第一次完整导出），关闭对话框；
  2. 立即再次按下「导出日志」并收敛（第二次完整导出，与第一次落在同一自然秒内）；
  3. 比较两次 `DebugStats.diag_last_export_path`。
- 期望结果（验收点 7 原文）：「连续两次完整导出的文件互不覆盖」。
- 实际结果：两次路径完全相同并相互覆盖。探针实测证据（qa_r292qa_probe.log）：
  `A=B=C:/Users/.../app_userdata/Infinite Fission/diag_v0_1_89_vc90_205043.txt`（两次导出均落在 20:50:43）。
- 根因：`autoload/debug_stats.gd:870-871` 文件名时间戳粒度为 HHMMSS（`Time.get_time_string_from_system().replace(":", "")`，无日期/毫秒），同秒两次导出必然同名，`FileAccess.WRITE` 直接覆写。
- 影响评估：真机手动流程（导出→关对话框→再按）基本不可能落进同一秒，且两次内容近乎相同，实际损失可忽略；但按验收点 7 字面判不通过。
- 归属：R205 时代既有行为，R292 明确未动 `diag_export()` 本体（多套件直调契约），非本次回归。建议后续轮次给文件名加日期段或毫秒/计数后缀（顺带解决跨天同时刻同名）。

### 观察记录（非缺陷）

**O1 探针诱发的 SCRIPT ERROR（`_apply_safe_area` 对已释放 `_root` 无守卫）——生产不可达，非 R292 相关**

- 现象：探针 7b-1（人为单独 `queue_free` 菜单 `_root`、MenuScreen 存活）之后，窗口 `size_changed` 触发既有绑定 `SafeAreaHelper.bind_reread → _apply_safe_area`（`menu_screen.gd:181`）对已释放 `_root` 写 `offset_left`，报 `Invalid assignment ... on a base object of type 'previously freed'`。日志：`tools/r292qa_runs/qa_r292qa_probe.log`。
- 归因：`_apply_safe_area`（R195 代码）不校验 `_root` 有效性。生产中 `_root` 只随整个 MenuScreen 一起释放，对象释放时窗口信号连接自动断开，该路径不可达；仅本探针人为制造「菜单活、_root 亡」的假状态才触发。与 R292 改动无交集（R292 不释放 `_root`、不调用安全区适配）。
- 建议（卫生级，可不修）：`_apply_safe_area` 入口加 `is_instance_valid(_root)` 守卫。

**O2 退出期 RID/ObjectDB 泄漏告警**：本套件与开发套件全绿日志均出现同类告警（对照 `tools/r292_runs/qa_r292_export_progress.log` 尾部），属本项目 headless 测试环境既有噪声，不据此立案。
